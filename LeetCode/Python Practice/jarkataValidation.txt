what is dbms in database

A Database Management System (DBMS) is essentially the software bridge between a user and a database. Think of it as a highly organized librarian: you don't go wandering through the stacks of books yourself; instead, you ask the librarian to find, add, or update information for you.

Without a DBMS, you’d just have a "database"—which is simply a collection of raw data—but no efficient way to manage, secure, or retrieve it.
How it Works

The DBMS accepts requests from an application or a user (often via a language like SQL), finds the data on the physical storage, and presents it in a way that makes sense.
Key Functions of a DBMS

    Data Storage Management: It handles the complex task of storing data on disks, so you don't have to worry about where the bits and bytes actually live.

    Data Security: It ensures only authorized people can see or change specific pieces of information.

    Concurrency: It allows multiple people to access the same database at the same time without "crashing" into each other or corrupting the files.

    Backup and Recovery: If the system fails, the DBMS provides tools to restore the data to its previous state.

Common Types of DBMS

Different data needs require different management styles. Here are the main players:
Type	Description	Examples
Relational (RDBMS)	Data is organized into tables with rows and columns.	MySQL, PostgreSQL, Oracle
NoSQL	Handles unstructured data like documents or graphs; great for "Big Data."	MongoDB, Cassandra
In-Memory	Relies on main memory (RAM) for ultra-fast data access.	Redis, SAP HANA
Methods for Interaction

Since you mentioned an interest in how to interact with these collections, here are the primary methods used in most relational systems to manipulate data:

    SELECT: Retrieves specific data from the collection.

    INSERT: Adds new records to the collection.

    UPDATE: Modifies existing data within the collection.

    DELETE: Removes records from the collection.

Why use UUID over String?

While you could store a UUID as a String, using the actual UUID type is better for several reasons:

    Type Safety: You won't accidentally pass a random string into a method expecting an ID.

    PostgreSQL Performance: PostgreSQL has a native UUID data type. When you use java.util.UUID in your Java code, Hibernate maps it directly to the native Postgres type, which is much more efficient for indexing and storage than a 36-character string.

    Automatic Generation: You can let Hibernate handle the generation for you so you don't have to manually create the UUID every time.
